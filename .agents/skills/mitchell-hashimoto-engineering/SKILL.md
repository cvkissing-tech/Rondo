# Mitchell Hashimoto：工具工程方法参考

本技能提炼公开方法，不代表本人、不是本人参与的代码审查。调研日期 2026-10-25；快速档：5 篇本人文章和 1 个原始访谈节目页面，未覆盖完整生涯。

## 回答工作流（Agentic Protocol）

1. **定位一条真实链路**：读调用入口、被调用模块和现有检查，写出输入→行为→可观察结果。涉及工具版本或当前协议，先查其官方材料并核对本机；人物文章不是接口规范。
2. **选择可演示增量**：从心智模型中选一个适用原则，给出本轮能运行的演示和明确未验证项。优先扩展已有工具；不要为了模仿人物更换语言、重写平台或增加 Agent 数量。
3. **执行并对照**：在隔离实验目录验证正常、失败和退出行为；记录真实证据。用“事实→框架推断→实现选择→验证结果”解释；没有执行的检查保持未知。

## 核心心智模型

### 模型1：用可见进展安排工程顺序
**证据**：终端项目按可演示组件推进 [S2]；进入陌生项目先获得可构建、可实验的入口 [S3]。
**应用**：本项目每轮交付一条可运行路径，如启动→发送→终态→退出；CLI 和测试都可成为演示。
**局限**：演示通过不能证明可发布、性能合格或所有平台兼容；这是推进方法，不是验收标准的替代。

### 模型2：把反复出错转成可执行反馈
**证据**：Agent harness 使用工具纠正重复错误 [S1]；Tripwire 主动触发错误恢复路径 [S4]。
**应用**：先复现实际失败，再补最小回归检查或修复共享实现。对于进程泄漏，要检查资源是否释放，而非只检查返回了错误。
**局限**：不为每个假想错误建立框架；特定 Zig 工具不能直接作为 Python/Windows 实现。

### 模型3：从一条用例追到基础，再用对照校准理解
**证据**：陌生项目采用 trace down / learn up 并重做近期小改动 [S3]；AI 采用过程用已完成工作校准 Agent 能力 [S1]。
**应用**：从一次请求追到传输、会话和进程；用已知样例对照实际协议结果，记录失败边界后再扩大支持。
**局限**：本人这两篇文章支持这一归纳，但不证明他对所有工程都采用同一流程；不要求重复所有人工劳动。

## 决策启发式

1. **先写本轮可观察终点**：借鉴 Ghostty 的早期 CLI 演示 [S2]；在本项目可表现为一条无需手工交接的实验命令，成功/失败均有证据。
2. **复现重复错误，修复环境或工具**：借鉴 harness [S1]；已知协议错误应留下失败检查，不只在提示中要求“更小心”。
3. **故意在资源分配之后注入失败**：借鉴 Tripwire [S4]；验证启动失败、中途断连、取消后的句柄/子进程清理，保留真实平台检查。
4. **状态由运行方明确报告**：借鉴程序状态协议 [S5]；优先协议完成/失败/等待事件，不能用输出安静、窗口标题或有回复推断完成。未验证支持的协议不自动启用。
5. **按真实可委派任务决定并发**：其文章偏好有限后台任务 [S1]，访谈摘要有持续使用 Agent 的描述 [S6]；本项目不把 Agent 越多等同于更好，遵循预算与用户选择。

## 本项目的适用与不适用

- 适用：Agent 调用入口、CLI 演示、停止/断连恢复、协议状态、复现上游缺陷和小型开源贡献。
- 当下可落实：让模拟器立即启动子进程，验证调用超时后它确实退出；让相同请求的“部分文本”和“协议成功终态”得到不同判断。
- 不适用：凭人物偏好决定模型排名、价格、WorkBuddy 未公开能力，或证明 Windows 进程隔离已经可靠。
- 学生学习：解释一条真实调用链和一个故障实验，避免只交付大量代码或要求用户盲目接受。

## 内在张力与反模式

- **张力一**：快速达到 demo [S2] 与主动验证冷门错误路径 [S4] 并存。实现范围可以小，已经实现的资源管理不能只靠目测。
- **张力二**：希望持续利用 Agent [S1/S6] 与限制并发、保护专注 [S1] 并存。不应把持续利用解读为无限循环或无人监管运行。
- 反模式：为未来多平台做大型抽象；把用户没体验过的“平台”当进展；用专家认可替代运行结果；照搬某篇文章时点的工具组合。
