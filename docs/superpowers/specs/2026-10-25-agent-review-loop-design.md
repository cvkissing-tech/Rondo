# Agent Review Loop：首版设计

日期：2026-10-25

## 目标

为一个用户完成可追踪的“实现 → 自动化检查 → 独立审查 → 用户选定意见 → 修复与回归”流程。在成本与限额约束下，首版采用 WorkBuddy + DeepSeek 实现与修复、Codex 强模型关键审查，不要求先做全 Codex 对照。实际模型版本、仓库访问能力和证据质量逐项记录，不构成质量排名或同等质量承诺。通过进程、Git、状态和验证的实际工程练习，形成可独立运行的开源作品。

## 使用边界

- 首版单人、本地交接工具、单任务顺序执行，角色可互换；Agent 自身是否调用云模型由其原有配置决定。
- 面向用户明确指定的实验 Git 仓库；实现任务使用独立工作目录。
- Python 3.11+，第一阶段仅标准库。
- 第一阶段不调用模型，不读取密钥，不安装全局软件。
- 真实 Agent 阶段只支持明确测试过的版本与运行模式；CLI 不在 PATH 不等于用户没有安装桌面版。
- 角色、模型、skills、工作目录、权限和登录方式分别核验；不要求把个人配置整体上传或复制。
- 原始运行记录可能包含私人资料，默认只留在本地，公开示例使用合成数据。
- 首版不承诺任意 Agent 接入、整个会话无损迁移或模型成本必然降低。

## 结构

Python CLI 与本地 MCP 服务负责接收任务与用户选择；共享进程执行函数处理输入输出与退出，直接启动 Agent 的适配单独验证。实现与审查使用不同会话和明确的权限；Git 快照提供交接基线，SQLite 记录任务与尝试，原始日志保存在本地运行目录。自动化检查的命令、版本、退出码与输出独立记录。

WorkBuddy 接入由用户在其界面发起，通过本地 MCP 获取实现或修复任务与提交结果；Codex 首先也作为 MCP 客户端，由用户发起审查。主动执行审查或推送至 WorkBuddy 在正式接口和账号权限验证后再评估。单纯检测到桌面进程不证明连接器、模型、skills 或实现任务可用；真实双 Agent 闭环需两边分别验证。

先落地第一阶段的进程执行模块。后续增加数据库和 Git 管理时，按真实需求扩展，避免提前建立通用插件系统。

## 第一阶段接口

`run_process(argv: list[str], cwd: Path, prompt: str, output_dir: Path, timeout_seconds: float) -> RunResult`

`RunResult` 字段：`status`、`exit_code`、`stdout_path`、`stderr_path`。`status` 只能为 `completed`、`failed`、`timed_out`。状态也写入 `output_dir/result.json`，字段路径为字符串。

此阶段 `completed` 只表示测试进程退出码为零。真实 Agent 接入后还要检查事件中的终止状态；代码任务是否完成另行依据验收结果判断。

## 进程行为

- `argv` 是参数列表，`shell=False`，不得将用户任务拼成 shell 命令。
- `cwd` 必须为已有目录；超时必须为正数；`output_dir` 必须为未存在的路径，禁止覆盖上一轮证据。
- 提示通过 UTF-8 stdin 传入；stdout 和 stderr 分别直接写文件，避免整个输出堆在内存里。
- 启动失败写 `failed`，退出码为 null，诊断写入 stderr。
- 超时终止并等待直接启动的进程；第一阶段测试进程不创建子进程。此阶段不承诺清理整棵进程树，接入真实 Agent 前必须完成目标平台的进程树取消验证。
- 不自动重试失败进程。重跑使用新目录；持久化状态不等于可以继续存活的进程。

## Git 与审查（后续阶段）

任务绑定基础提交。交接包含目标、约束、快照标识、差异、检查命令、退出码、日志和未执行的检查。包含新增文件，不能只捕获普通 `git diff`。产生新快照后，旧审查标为过期。

审查基于只读目标快照或可验证的只读权限；Git worktree 只隔离工作目录，不提供执行权限隔离。工具不自动提交、合并、推送或发布。用户选择意见后只进行一轮修复，之后重新审查由用户发起。

## 运行记录（后续阶段）

任务状态与单次进程状态分开。任务可处于 `ready`、`implementing`、`reviewing`、`awaiting_user`、`repairing`、`finished`、`failed`、`cancelled`、`interrupted`。重启后，未能确认仍在运行的任务标为 `interrupted`，不自动重发付费请求。

## 验收

1. 第一阶段：不访问网络，成功、非零退出、启动失败、超时、中文与空格路径、重复输出目录均有实际检查。
2. 第二阶段：WorkBuddy + DeepSeek 完成领取任务和提交结果，Codex 完成一次独立审查；记录版本、模型、配置来源、权限与能力，不把命令 `--help` 成功或桌面进程存在当作账号可用。
3. 第三阶段：同一快照交接，审查返回可定位的意见；新文件包含在证据中。
4. 第四阶段：用户选择后修复，旧审查失效；取消与重启不遗失已有日志、不悄悄重发任务。
5. 发布阶段：他人可按 README 跑通合成示例；离线测试与真实模型验证分别报告。

## 预算与停止条件

同一任务默认一次完整 Codex 审查，用户选定意见修复后至多一次针对修改及相关影响的复查，上层执行合计上限为两次。不自动重试失败或限额请求，不在无进展时循环互评。耗时、退出原因和平台报告的用量均记录；费用或剩余额度无法读取时记为未知。

上层执行次数不等于模型请求次数或 token 数，不能单靠两次上限承诺成本。接入阶段另设进程超时，并确认具体平台是否提供可执行的轮数或用量约束。方案检查仅在跨模块或高影响决策时使用 Codex，单独记录预算。达到上限或限额、没有进展时停止并保留证据；关键问题未解决时保持未完成，不静默换模型继续消费。

## 审查与修改分工

原实现 Agent 保留任务上下文并负责修改，另一个独立会话审查。审查者应能读取需求、完整目标代码及相关调用链，在受控环境中运行检查；不默认接收实现者整段推理，必要的项目约束和事实必须共享。审查报告需关联快照、文件位置、触发条件、影响和证据，区分已复现缺陷、静态疑点和未运行检查。用户选择后交回原实现者；对有争议的意见先尝试最小复现。缺陷修复尽可能留下修复前失败、修复后通过的检查，不能通过删除、跳过或削弱验收断言换取通过。

测试执行与结果独立记录，不将另一个模型的赞同视为正确性证明。同模型不同会话仍可能有共同盲点；不同模型也不保证更好。通过带已知缺陷与无缺陷对照的固定样例，比较有效发现、误报、复现证据和修复后回归，再选择审查配置。用户最终接受需求取舍，工具不要求用户承担全部代码缺陷识别。
