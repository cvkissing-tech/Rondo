# Agent Review Loop：开源借鉴与复用清单

日期：2026-10-25。本文承接已讨论的首版范围，记录来源、采用方式和验收要求；不是已经完成接入或移植的声明。

## 负责人决策

保持独立的 Python 项目，交付本地 MCP 服务与命令行入口。先验证 Codex 与 WorkBuddy 共享一条合成任务，再增加代码快照、审查和返修。第一版由用户在各客户端发起操作；主动唤醒 Agent 作为独立的运行适配能力验收。

直接复用官方 MCP SDK、Git、SQLite 与仓库已有进程模块。对业务模块先确认依赖和行为：能独立运行、能带着必要验证一起迁入的模块可以直接采用；Go/TypeScript 实现若依赖整套服务，则提取必要规则，在现有 Python 技术栈内实现。首版不引入完整上游产品为运行依赖，也不把多个项目的数据结构拼成通用框架。

第三方授权按用户已说明的前提处理。保留来源与修改记录用于定位问题、解释实现和跟踪上游变化。

## 逐模块采用方式

### 1. 任务领取：参考 rhizome 的事务与竞争测试

来源：[初始数据库结构](https://github.com/Odrin/rhizome-mcp/blob/03fffd7d1410ddccadf7c199f5d6e796a497b1f0/internal/migrations/sql/001_initial_schema.sql)、[跨进程领取竞争测试](https://github.com/Odrin/rhizome-mcp/blob/03fffd7d1410ddccadf7c199f5d6e796a497b1f0/integration/claim_race_test.go)。

采用数据库事务、唯一性约束与预期版本检查。stdio 客户端可能分别启动服务进程，因此必须连接同一明确的数据库路径；Python 进程内的锁不能代替数据库约束。仅支持本地同一可信用户，Agent 标签不充当身份认证。

首先实现当前阶段的唯一领取；真实任务阶段增加有期限的占用与恢复。过期占用不得继续提交，恢复必须产生新尝试，不能悄悄重发模型请求。

验收：两个独立进程竞争同一任务阶段，恰好一个成功；另一方收到明确冲突，已有结果不被覆盖。增加过期恢复后，再证明旧领取者不能完成新尝试。

### 2. 审查：参考 rhizome 的版本前提，增加代码快照绑定

来源：[审查流程契约](https://github.com/Odrin/rhizome-mcp/blob/03fffd7d1410ddccadf7c199f5d6e796a497b1f0/docs/09-review-workflow.md)。

上游文档的目标是任务版本、事件位置和产物引用；这不证明它会自动检测工作目录中的任意代码变化。我们的审查另行关联基础提交、快照清单与内容摘要。快照必须覆盖所选新增文件、修改和删除；忽略文件默认不收入，秘密文件不因“完整快照”自动收集。

审查者读取固定快照及必要上下文。产生新快照后保留旧报告，明确其适用版本；最终接受当前工作前再次核对代码与审查目标，不只依赖界面上的“通过”。

验收：审查 A 后修改为 B，A 的通过不能用于接受 B；新增文件没有遗漏；更换任务描述的版本也不能复用旧审查。

### 3. 重复提交：借鉴 Relay 的作用域，使用 SQLite 持久化

来源：[请求重放实现](https://github.com/AgentWorkforce/relay/blob/c3a92d9c179972963756ebce3fcd106679302934/packages/cli/src/cli/mcp/request-replay.ts)。

该文件区分进行中的 JSON-RPC 请求重放与显式幂等键，并在内存里短期保留结果。我们采用“明确重试标识、区分不同操作”的规则；为支持多个服务进程与重启，业务提交的幂等记录写入 SQLite，并与状态更新在同一事务提交。MCP 传输请求 ID 不充当持久业务操作 ID。

我们的幂等键限定在任务、阶段和尝试内，并保存请求内容摘要；同键同内容返回已有结果，同键不同内容返回冲突。这是本项目要求，不声称与上游的重放行为完全相同。

验收：重复提交不产生重复结果；重启后重试返回原结果；两个进程同时重试仍只执行一次数据库变更。对实际模型调用不宣称严格只执行一次，也不自动重放。

### 4. 上下文：采用 Guild 的交接摘要和预算意识

来源：[交接摘要存取](https://github.com/mathomhaus/guild/blob/13130ff34aec375927e4ab6418739c9667ebf74d/internal/quest/brief.go)、[MCP 描述预算测试](https://github.com/mathomhaus/guild/blob/13130ff34aec375927e4ab6418739c9667ebf74d/internal/mcp/budget_test.go)。

默认返回任务目标、约束、当前阶段、最新结果、下一步和证据引用；详细日志与历史按需读取并分页。交接摘要由 Agent 提供，真实状态由服务记录和验证，摘要不能替代代码与测试证据。

控制工具目录和返回内容大小。上游测试使用英文字符估算 token；不把这一估算照搬为中文或不同模型的精确 token 数。首版验证字节上限、分页与截断标识，真实上下文消耗在客户端实验中记录。

验收：大量历史与长日志不会被默认全量返回；新会话能找到下一步及证据；需要进一步阅读时有明确入口。

### 5. 进程取消：参考 Agent Orchestrator，补齐现有模块

来源：[Windows 进程组与子进程树清理](https://github.com/OrchestratorInc/agent-orchestrator/blob/3e59b0394ff72b408def75b22a596f2dcac7efb7/backend/internal/adapters/chatdriver/acp/process_windows.go)。

上游使用进程组标志及 taskkill /T，失败后回退到直接终止进程。参考其平台分支和清理目标，不把回退行为视作整棵进程树已清理的证明。现有 runner 继续保留；在它承担真实 Agent 子进程执行前补齐取消验证。

验收：合成父进程创建子进程后，取消只影响本次启动的进程树；父子均退出，日志仍可读取。清理无法确认时明确记录，不报告完全取消成功。

### 6. MCP 与界面：复用 SDK，参考 Superset 的职责边界

来源：[MCP 服务器实现](https://github.com/superset-sh/superset/blob/6277058f17204959d1d42d8c963885396b0ad398/packages/mcp/src/server.ts)。

使用官方 Python MCP SDK。工具描述说明输入、状态前提和下一步；共享任务与运行调度分别验收。第一条流程只需要创建、读取、领取、提交结果这些工具；代码快照与审查工具随对应阶段增加。

Superset 的完整桌面工作区、云端组织、远程主机与定时自动化不进入首版。界面需求由真实使用中的操作困难决定。

## 每次移植或改写的交付要求

1. 标明来源提交、具体文件、直接复用还是行为改写，以及必要依赖。
2. 写清本模块的一条行为规则与失败条件，移植必要的验证场景，不机械搬运整套测试框架。
3. 在本项目环境运行检查；上游有测试文件不能记成本项目已通过。
4. 记录相对上游的差异和适用边界。发现适合独立修复的上游问题时，另做可复现贡献，不承诺 PR 必然合并。

## 当前进度和下一项工作

本清单创建时完成固定提交的源码阅读和复用规划，没有移入第三方业务代码，没有运行上游测试，也没有完成客户端接入。

下一项仍是单一任务：最小 MCP 服务与 SQLite 记录，让两个独立客户端完成一条合成任务的创建、领取、提交和读取；并验证跨进程竞争与重复提交。通过后再进入 Git 快照和审查，避免同时展开多个子系统。

开发进展：上述 MCP 与 SQLite 基础已在 0.2.0 实现并通过 SDK 双客户端验收，业务规则采用 Python 实现，未复制 Go/TypeScript 模块。真实产品接入仍待验收，见[本地验收记录](../../learning/2026-10-25-acceptance.md)。

0.7.0的一键任务入口继续直接复用现有prepare_workspace和[Git原生worktree](https://git-scm.com/docs/git-worktree)，以--detach创建固定提交的独立工作目录；没有增加GitPython或另一套仓库管理器。MCP继续复用已安装官方SDK。新代码只连接任务记录、工作目录和既有审查，不移植其他平台的账号、界面和调度系统。见[第8课](../../learning/08-start-task.md)。
