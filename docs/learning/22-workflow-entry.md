# 22：执行入口为什么会随着计划消失

此前的小窗口布局会用完整计划替换聊天区，而“采用计划并执行”按钮恰好属于聊天底部。隐藏聊天时，按钮一起被隐藏。后台自动执行、审查和一次返修的代码没有删除，但用户失去了明显的启动入口。

最终布局把状态与确认动作分开，继续使用Jean按钮和现有主题：

```text
task-workbench
  WorkflowBar：实际状态、协作顺序
  ResizablePanelGroup
    TaskTimeline：讨论与进展，输入框上方采用计划
    WorkspaceInspector：计划、文件、改动、会话，计划底部固定采用栏
```

`WorkflowBar.tsx`的状态栏不放启动按钮；同文件的`PlanAdoption`复用原来的`startExecution`，由App传给聊天和计划面板。采用版本的后台核对、执行、检查、审查和至多一次返修沿用原实现。宽窗口两处都是当前计划的同一个动作；小窗口切换完整计划时不会失去入口，也不必回到顶部操作。

另一个相关问题是已读取的差异会抢占`taskFlow`分支：一份针对当前代码的有效计划，本来应能执行，却因查看过改动而被引向人工审查。现在只有没有计划时，差异才走这个兜底分支；计划过期和旧执行收据继续保留原来的阻断行为。

`flow-check.mjs`包含这个有意义的回归：有当前计划、同时已读取差异，动作仍为execute。`workflow-entry-smoke.mjs <ready-task-id> [database]`只读备份指定数据库，在独立Electron配置下核对顶部无采用按钮、聊天动作在输入框上方、窄窗口计划底部动作在滚动时固定，以及未创建执行作业。它不会点击付费启动按钮。最初的入口回归使用2048任务副本；最终位置回归改用独立合成计划，因为用户的真实2048任务已开始执行。模型调用和派发数均为0。
